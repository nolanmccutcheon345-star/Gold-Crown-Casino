# Step 5D browser recovery profiling harness

This is authored QA, **not a browser PASS receipt**. Root executes the page through the supported browser UI.

- `node tests/step5d-browser/build-frozen-v9.mjs`: reproducibly bundles the actual saved Version9 source `104b9d64b60276866a25f8bf65827efa65e1df2a`, including production UI, and records source/bundle hashes. `.bin` assets avoid development-server transformation; bytes are checked before typed-Blob module/CSS loading.
- `node tests/step5d-browser/build-fixtures.mjs`: extracts exact0/100/500/1000/5000/10000-hand canonical prefixes from the retained10k source archive. All copied record bytes/hash chains remain unchanged; the subset manifest ends at a closed-session boundary. Streaming seed avoids retaining another full481MB object graph merely for fixture setup. Generated source-fixture raw byte hashes are verified by the browser before `current` is committed.
- `node tests/step5d-browser/capture-source.mjs`: capture current production source hashes immediately before candidate profiling. This is provenance, not execution proof. Keep production inputs unchanged during measurement.
- Open `/tests/browser/step5d-recovery.html` on the managed preview. Select exact count, Saved Version9 or Candidate, and cold-closed or active-pending mode. Click Run. A fresh iframe mounts the actual application and uses only the explicit randomly named QA IndexedDB. It deletes only that exact test database after result collection.
- Download full JSON or read all `#evidence-chunk` choices (40000characters each). `#result` is a summary, not full stage evidence.

Pending mode first loads the canonical subset using frozenV9, creates a legitimate heads-up hand using the authoritative engine, Hero calls, a bot decision is durably sampled, and the hand is paused. It closes the connection and mounts a fresh production application/controller. The exact active-state digest (including pending draw/decision and committed game) must survive. This is an interrupted-controller/reload equivalent inside a fresh iframe, **not an actual OS/browser process kill**. The UI stays paused during profiling to avoid mixing automatic actions with startup measurements.

The actual loading shell must hide unverified wallet values. Controller ready time, first actual UI paint after verified readiness and secondary-statistics completion are distinct. Current versions perform the complete canonical/financial audit before Ready; no background audit is falsely claimed. If that contract changes, update the harness explicitly. Independent wallet/table/net/unique-event/settlement counts are asserted. Initial module/network/fixture setup is separately disclosed, not folded into storage recovery. Browser heap is a coarse shared Chromium estimate; long tasks are not INP. No browser GC attribution or physical-phone inference is made.

Local checks executed in the author lane: frozen source build; six-size fixture extraction (raw hashes/counts and exact session boundaries); TypeScript and scoped ESLint. Browser checks remain NOT_EXECUTED until the integrator runs them and retains resulting JSON. No production code changes in this lane.

Standalone comparison: use the parent page’s **Open standalone profiling page** link after selecting count/reader/state. Its fresh identity is separate from the embedded run. The same frame code runs at top level and exposes `#qa-result`, `#qa-evidence-chunk`, `#qa-evidence` and `#qa-download` after completion. Existing timings are preserved. `browsingContext` and visibility fields distinguish measurements; observed animation-frame delay is not attributed to processing or throttling without evidence. Browser evidence has not been executed by this author lane.

Packed-storage comparison: `storage=legacy` always seeds the original archive and, for a candidate with automatic packing, includes its first installation in measured readiness. `storage=packed` is available only for Candidate; it first fully restores and atomically installs the packed descriptor, records that preparation cost, closes the controller and measures a fresh load. Installation cannot change the wallet, hand count or active pending-state digest. The measured candidate port separately runs `auditCanonicalArchive()` after UI/statistics readiness, checks wallet/hand agreement, and records retained-archive audit status and completion time. This is an explicit QA-triggered independent audit, not a claim of automatic background execution. Full required recovery verification still precedes Ready. Baseline does not implement or need this optional duplicate-storage audit.

## Fresh-document comparison (opt-in; previous results remain same-document)

Select **Document → Fresh document after fixture preparation** (`#fresh = 1`) before opening the standalone link or running the iframe. Both reference and candidate follow this route. Preparation seeds the exact canonical fixture, establishes the requested pending state, and optionally installs the verified packed transport. It closes all database connections, writes a hashed, parameter-bound preparation receipt under 16 KiB in sessionStorage, then uses real `location.replace` to load a new document with `phase=measure`. The measured document verifies that receipt and restores the existing isolated IndexedDB database without reseeding, reconstructing the preparation controller, or retaining its module/projection caches.

Existing fields retain their original meaning: `safeGameplayReadyMs` starts at mounting the production controller/UI, and the required canonical financial audit precedes Ready. New `navigationToSafeGameplayReadyMs` / `navigationToSecondaryStatisticsReadyMs` include the fresh document's module/runtime startup. `freshDocument`, `recoveryDocumentMode`, `setupReceiptVerified`, and `freshDocumentNavigation` make the mode explicit. Old receipts are not relabeled. The final run independently checks the recovered wallet, hand tail/count, active pending digest and full archive as before, then deletes only its exact test database and preparation receipt. This is a new JavaScript document, not a restarted browser process or forced OS-cache/GC reset; coarse Chromium heap may still include renderer-managed memory. No browser execution is claimed merely from authoring this option.

Fresh-document measurements additionally install a buffered Long Tasks observer before runtime imports. `navigationMaximumBrowserTaskMs` covers that new document through statistics readiness, including startup/import work; `maximumBrowserTaskMs` remains the original mount-to-statistics interval. `navigationHeapAtModule` is a coarse initial observation. Both navigation task fields remain separate from the optional retained-archive audit and cannot be reconstructed for old same-document receipts.
