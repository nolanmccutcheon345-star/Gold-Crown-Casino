# Step5E recovery storage verification

The production storage path keeps canonical v2 records, packed replicas and migration/rollback backups. Acceleration uses a separately versioned financial checkpoint plus at most63 ordered journal revisions. Every commit writes canonical records, the new journal/checkpoint and the current head in the same fenced IndexedDB transaction. The current and previous acceleration generations are retained; older acceleration records alone are retired atomically after a replacement checkpoint is written.

Before gameplay, recovery verifies the checkpoint/journal digests and identities, exact current canonical manifest/header, every canonical financial ledger/session/import record and its outer chain, independent financial replay, the compact all-hand financial index, the120 actual resident hand records, statistics and public-only bot memory. A key-only inventory checks that archived full hand records exist. Historical hand body bytes outside the resident tail are explicitly **not audited** by that inventory. Indexed `readHand` verifies requested records; `loadFullHistory` and `auditCanonicalArchive` perform complete independent canonical reconstruction. No recovery function computes poker winnings or alters the engine's cards/actions.

The bounded resident tail is also checked against its original canonical rows or existing independently verified packed replicas. Its segment chain must reach the current canonical manifest tail. A valid checkpoint cannot conceal damage to both archive copies of a resident record. The `recovery.residentArchive` stage measures this necessary work. An interrupted optional packed installation returns the already verified original save without starting a second installation that would mutate storage after the first aborted.

`checkpoint.test.ts` tests the transport with real engine-generated snapshots and independent financial audit hooks. `browser-atomic.test.ts` uses an asynchronous atomic transaction reference and isolated projection hooks; it is **not browser execution**. `production-integration.test.ts` uses the real compact finance/statistics/memory hooks and124 actual completed hands, including subsequent settlement and interrupted bot recovery. Browser/device claims require the separately executed release harness.

## Storage bounds and limitations

IndexedDB read/write transactions request `durability: strict`; the existing fallback uses default durability if the options overload is unavailable. The [IndexedDB specification](https://www.w3.org/TR/IndexedDB/#transaction-durability) defines strict durability as a hint to verify writes reached persistent media before completion. It improves crash resistance but is not a universal hardware guarantee. No asynchronous hashing is performed while a write transaction is live.

Browser storage remains per-origin local guest data. [MDN's storage guidance](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria) documents quota errors, best-effort eviction and user-cleared/private-session data. The existing `requestProtection()` requests persistent storage; availability/grant is browser-controlled. Atomic write failures preserve the previous committed state and surface the error. This is not cross-device backup or synchronization, and browser-cleared origin storage cannot be recovered from a checkpoint stored in that same origin.

Canonical archive growth is proportional to actual recorded history. Acceleration retains two checkpoint generations and their bounded journals. The compact full financial ledger/index still grows with hand count; this implementation deliberately verifies those financial records before play. Only large historical frame/card bodies are omitted from ordinary startup. Local hashes detect corruption and mismatched state; they are not authentication against an adversary who can rewrite every local record and recompute all hashes.

## Avoiding unnecessary large first-conversion work

The retained [Step5D profile](../step5d-recovery/REPORT.md) measured27.584 seconds encoding10,000 packed hand replicas, separately from mandatory canonical recovery. Step5E fast checkpoint recovery does not consume those whole-archive packed replicas. A first conversion with more than120 old hands therefore performs the full canonical audit and installs the verified financial checkpoint directly; it does not automatically encode/write a second copy of every archived hand. Existing packed copies remain untouched, new games retain their existing representation, and explicit `optimizeStorage()` remains available. Small archives retain the prior automatic packing behavior.

`production-integration.test.ts` executes124-hand unpacked v2 and v1 first conversions. The v2 test records executed stage names and requires the full audit and recovery-checkpoint preparation while rejecting any whole-archive packing stage; it checks unchanged original rows, fast reload, a subsequent125th settlement and the frozen V7-R reader's complete canonical restoration. The v1 test verifies the original populated upgrade backup. These are transaction-reference checks, not a claimed browser speedup. Actual first-installation and subsequent-startup timings remain separate release measurements.
