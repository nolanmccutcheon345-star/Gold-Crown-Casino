# Step5C verified upgrade and controlled compatibility rollback

Z03 remains the original criterion: “Previous working release can be restored
with preserved valid user histories and no duplicated money or orphaned event.”

The unchanged published Version 7 (`a0bfc0950771a6dc1b786e00c13be7f3485b8dcb`)
cannot understand segmented envelopes or the newer pending decision policies.
**Redeploying unchanged Version 7 is not the recovery procedure.** Copying
`pre-segment-v1` over `current` would discard post-upgrade events and is forbidden.

The recovery artifact is explicitly **V7-R**: the eight exact imported UI/CSS
files from published V7, bundled with the frozen tested Version8 engine, session controller, storage
reader and immutable policy implementations from
`f54cacfb0aa3c861313b691e773a6716379c50a0`. It
restores the previous interface and can finish an active hand, settle once,
cash out and create another session using every latest valid record. It reverts Step5C runtime changes as well as the newer interface. It is not the
unchanged Version7 binary, a schema downgrade, or a repair of arbitrary corrupt
storage. Known Version8 cold-recovery costs return (previously 39–56 seconds at
10,000 hands), and the prior interface has its historical feature/performance
limits. A defect already present in this frozen baseline requires a separately
fixed recovery candidate and verification; this artifact cannot claim to fix it.

## Upgrade protections

Before the first incompatible envelope-v1 → envelope-v2 commit, the implementation
verifies the original checksum and full original ledger, migrates only the known
schema additions, and compares every resulting canonical byte (except the single
revision advance). It prepares a checksummed migration receipt binding source and
target schema/envelope versions, revisions, original checksum and new manifest
checksum, plus wallet, record counts and hand/ledger tails. Exact original envelope,
receipt, all new segments and current manifest commit in **one** fenced native
IndexedDB transaction. Abort publishes none. Retry advances once. Previous schema
backups remain retained.

`BrowserPersistence.inspectUpgradeBackup()` fully revalidates the preserved backup
and its receipt without writing any current state. This explicit audit does not run
at every ordinary startup. Already-segmented Version8 saves with no receipt are
truthfully reported as having no verified pre-upgrade receipt; they remain readable
and playable through V7-R. No fabricated historical backup is created. Existing
full canonical validation and multi-tab revision/lease fences remain mandatory.

## Build and verification

```sh
node tests/step5c-rollback/build-recovery-release.mjs
npx vitest run tests/step5c-rollback/rollback.test.ts \
  tests/step5b-performance/browser-storage.test.ts \
  tests/step36/browser-storage-migration.test.ts \
  --reporter=json --outputFile=tests/step5c-rollback/vitest.json
npx tsc --noEmit
```

The generated manifest pins each of 95 compiled project files by SHA-256 and labels
its source as published V7 UI or saved V8 runtime. Both immutable Git commits are
recorded. Tests compare every source hash to those exact historical Git objects,
not to current candidate bytes. Rebuilding after candidate changes does not change
the recovery artifact. The generated executable and CSS are verification/recovery
artifacts, never imported by the ordinary application. Only generated bytes are
excluded from source lint.

Actual native-browser execution: open `/tests/browser/step5c-rollback.html`, click
**Run isolated recovery rollback** (`#rollback-run`), read `#rollback-status` and save
`#rollback-evidence`. The harness uses only unique `ai-texas-step5c-rollback-*` stores;
it does not access production guest data. It creates actual V7 settled hands plus a
pending decision, aborts the native migration after its receipt write, retries,
appends post-upgrade hands/top-up/cashouts/adjustment/pending1.6, verifies unchanged
V7 refuses without modifying data, opens V7-R, commits the saved action once, and
uses V7 interface Fold / New session / End session controls. Candidate then restores
the exact newer state; pre-upgrade backup is still independently verified. Unknown
schema refusal and actual isolated-store cleanup are required. Browser results are
NOT_EXECUTED until the integrator executes this page and saves its evidence.

## Deployment and rollback procedure

1. Freeze the candidate Git source; run full release gates and the above old/new
   populated-data cycle. Rebuild the pinned V7-R baseline. Retain its
   manifest and generated files with the release evidence.
2. Save and publish the normal candidate only when all mandatory R1 gates pass.
   Observe recovery errors, unexpected balance changes, duplicate settlements,
   failed session controls and material usability regressions. Any confirmed
   critical integrity issue stops new release approval and triggers investigation.
3. If the defect is absent from the tested frozen Version8 runtime and Version7
   interface, package V7-R's generated directory, retaining the **same** Site
   project ID. Its `.openai/hosting.json` uses static directory `.`. The Site owner
   saves/publishes that artifact as an explicitly identified recovery version;
   never present it as unchanged Version7. No production deployment is performed by
   the build/test script.
4. After deployment, verify guest opening, latest bankroll/session/history, pending
   action identity and legal play/cashout. No schema rewrite, data import, backup
   overwrite or balance reset is needed. Multi-tab fences continue to protect the
   store. Preserve all records if validation refuses; do not force-start gameplay.
5. For failures also present in the frozen baseline, incompatible data, or actual
   corruption, do not use V7-R blindly. Keep affected play fail-closed, inspect verified snapshots
   and immutable segments, fix the relevant module, replay full integrity checks,
   and test a separate recovery build against actual cloned pre/post failure saves.
6. When the normal candidate is repaired, it reads V7-R's continuing format2/schema4
   saves unchanged. Verify exact record identities and financial reconciliation
   before resuming. Code rollback and data-schema rollback are separate operations;
   this procedure intentionally requires no lossy data downgrade.

No physical iPhone, real-user calibration, deployment or screen-reader testing is
implied by these automated/reference and isolated browser checks.
