ACCELERATED BUILD DIRECTIVE
AI Texas Hold Em — V7 Accelerated Execution
Directive
Purpose: Shorten elapsed development time and avoid unnecessary rework
while preserving every applicable V7 requirement, all 302 specified acceptance
tests, the 86-ID future-feature register, and all cash-game and tournament re-
lease gates. This is an execution addendum, not a V8 scope revision. The
V7 poker rules, financial truth, opponent privacy, evidence classifications, and
release blocks take precedence if anything here conflicts.
1. Optimize the critical path, not the quality bar
Use four parallel implementation workstreams under one integration owner. The
implementation owner controls shared schemas and merges. Agent A owns game
authority, B owns presentation, C owns bot policy, D owns independent tests
and integration evidence. Before parallel edits, the integration owner freezes a
minimal versioned interface contract and golden test fixture format. Contrib-
utors use isolated branches/worktrees (where available), never write the same
shared core file simultaneously, and submit working changes with tests. A ded-
icated integration job validates every merge. Parallelism is opportunistic: do
not run tasks concurrently when they depend on unfinished decisions; do not
add an army of agents that increases merge conflicts or review burden.
2. Contract-first interfaces (freeze after first joint review)
• GameState — canonical seat, button, blinds, stacks, street, board, current
contribution, pending actor, committed pot, hand ID, revision and rule-
profile version.
• GameCommand — only legal user/bot actions and explicit seat/wallet com-
mands; contains a single-authority revision or decision ID.
• GameEvent — immutable authoritative event and ledger transition; none
may be generated by animation, UI state, or bot policy directly.
• LegalActionSet — fold, check, callAmount, minRaiseTo, maxRaiseTo,
full/short all-in conditions and reopening state. Bet/raise controls always
display raise-to total, not ambiguous extra chips.
• BotObservation — own private cards and permitted public information
only; no Hero secret cards, unrevealed opponents or future deck.
• BotDecision — action+size sampled once for a uniquely identified deci-
sion, validated by engine before committing.
• RuleProfile — room/cash/tournament distinctions and rake/ante/button/straddle/payout
versions, frozen per hand.

4. Reuse proven components instead of rebuilding every-
thing
• Consider PokerKit (Python) as a version-pinned, development-time in-
dependent poker state/evaluator oracle for compatible NLHE fixtures. Do
not assume it covers every house rule, and do not require Python in the
user’s browser.
• Use Vitest + fast-check for generated legal-state and invariant/property
tests: chip conservation, 52 unique cards, idempotent commit, single pay-
out, valid actors, round termination and replay consistency.
• Use Playwright for automated real-browser table journeys (configure ->
play hand -> showdown -> history -> cash out -> reload), responsive
viewports and trace-on-failure.
• Use GitHub Actions or equivalent CI for parallel lint/build/unit/oracle/browser
groups. Fail any merge on relevant critical tests.
• Use established state/storage and UI building blocks only after checking
licensing and actual compatibility.
Avoid building a custom AI solver,
generic multiplayer infrastructure, or an in-house animation engine in R1.
5. Test continuously but allocate test cost intelligently
Every change (fast gate): Typecheck, lint, build, targeted unit tests, fixed
smoke fixtures for minimum raise, side pot, one showdown, bankroll settlement,
forbidden hidden-card reads, and one browser hand. Keep this set small enough
to run often.

9. Explicit safeguards against speed-induced defects
• No multiple agents editing the rules reducer or financial ledger simultane-
ously.
• No heuristic bot policy may bypass legal-action validation.
• No new feature may introduce a second source of pot/stack truth.
• No opponent can use folded mucked cards or Hero private cards; a client-
only game is not cryptographically secure against developer inspection.
• No invented solver EV, human-calibrated labels, or real-world win-rate
predictions.
• No merging a critical bug merely because UI looks polished or simulated
win rate seems plausible.
• No launch of R2/R3 until release-specific financial and rules invariants are
executed and passed.
• All V7 features remain in scope at their assigned milestones; sequencing
is not scope reduction.
10. Effort reduction estimate — assumptions, not guaran-
tees
V7 estimates: prototype 25–60 active engineering hours; polished synthetic cash
R1 150–350; Sit & Go +60–150; MTT +170–450; cash+tournaments ~380–950+.
With disciplined interface contracts, useful existing libraries, ready-to-run CI
and 2–4 genuinely independent agents, conditional planning targets might
be: prototype 20–45, R1 115–280 total, Sit & Go +45–120, MTT +130–350,
and combined ~290–750 active engineering-equivalent hours. These are scenario
estimates, not observed productivity gains or a promise about the amount of
time one Work chat needs. Parallel execution may shorten elapsed calendar
time beyond effort savings, but merges, reviews, real-device tests and missing
human-play data remain nonparallelizable bottlenecks. If Work only supports

11. Definition of success
Each release must be runnable, not just documented. The R1 test is repeat-
edly playing credible Hold’em against controlled but non-cheating synthetic
opponents, with accurate stats, persistence, replay, and evidence-backed poker
legality. R2 and R3 add genuine tournament modes without changing the cash
engine’s core invariants. The project is never described as externally human-
realistic until it passes an independent human-data protocol.
